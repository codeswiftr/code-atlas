# Alert Runbook for Code Atlas

This document provides procedures for responding to alerts generated by Code Atlas monitoring system.

## Alert Categories

### Critical Alerts

#### ServiceDown
**Trigger**: Code Atlas API service is down for >1 minute

**Response Steps**:
1. Check service status: `curl http://localhost:8000/health`
2. Check logs: `docker logs code-atlas-api` or review application logs
3. Verify dependencies:
   - FalkorDB/Redis is running: `redis-cli ping`
   - Database connection is working
4. Restart service if needed: `docker restart code-atlas-api` or restart application
5. If persistent, check system resources (CPU, memory, disk)

**Resolution Time Target**: <5 minutes

---

#### CostThresholdExceeded
**Trigger**: Daily cost exceeds $50

**Response Steps**:
1. Review cost metrics: Check Grafana cost tracking dashboard
2. Identify high-cost operations:
   - Review `code_atlas_cost_total_usd` by model and operation
   - Check for runaway processes or large batch jobs
3. Take action:
   - Pause non-critical processing
   - Review and adjust cost limits in configuration
   - Investigate why costs increased
4. Notify stakeholders if cost is unexpected

**Resolution Time Target**: <1 hour

---

#### DatabaseConnectionFailure
**Trigger**: Database connection errors detected

**Response Steps**:
1. Check FalkorDB/Redis status: `redis-cli ping`
2. Verify connection string in configuration
3. Check network connectivity
4. Review database logs
5. Restart database if needed: `docker restart falkordb`
6. Verify connection pool settings

**Resolution Time Target**: <10 minutes

---

### Warning Alerts

#### HighErrorRate
**Trigger**: Error rate >5% over 5 minutes

**Response Steps**:
1. Check error breakdown by component and type in Grafana
2. Review application logs for error details
3. Identify root cause:
   - Check for configuration issues
   - Verify external API availability (if using LLM)
   - Review recent code changes
4. Fix issue or implement workaround
5. Monitor error rate until resolved

**Resolution Time Target**: <30 minutes

---

#### HighAPILatency
**Trigger**: 95th percentile API latency >1s for 5 minutes

**Response Steps**:
1. Check which endpoints are slow: Review endpoint usage metrics
2. Check system resources (CPU, memory)
3. Review slow query logs (if available)
4. Check database query performance
5. Consider:
   - Scaling resources
   - Optimizing slow queries
   - Implementing caching
   - Rate limiting aggressive clients

**Resolution Time Target**: <1 hour

---

#### HighCostPerSession
**Trigger**: Average cost per session >$0.05 for 10 minutes

**Response Steps**:
1. Review cost per session histogram
2. Identify high-cost sessions:
   - Check session sizes
   - Review LLM usage patterns
3. Investigate cause:
   - Large sessions requiring more tokens?
   - LLM model changes?
   - Configuration issues?
4. Adjust configuration if needed:
   - Reduce max tokens per session
   - Switch to more cost-effective models
   - Adjust chunking strategy

**Resolution Time Target**: <2 hours

---

#### HighCPUUsage
**Trigger**: CPU usage >80% for 10 minutes

**Response Steps**:
1. Identify high CPU processes
2. Check for:
   - Background processing jobs
   - Long-running queries
   - Resource leaks
3. Review processing queue size
4. Consider:
   - Scaling horizontally
   - Optimizing resource-intensive operations
   - Reducing concurrent processing

**Resolution Time Target**: <1 hour

---

#### HighMemoryUsage
**Trigger**: Memory usage >2GB for 10 minutes

**Response Steps**:
1. Check memory usage breakdown
2. Identify memory-intensive operations:
   - Large session processing
   - Batch operations
   - Caching overhead
3. Review for memory leaks
4. Consider:
   - Increasing memory limits
   - Optimizing batch sizes
   - Clearing caches
   - Restarting service

**Resolution Time Target**: <1 hour

---

#### LowDiskSpace
**Trigger**: Disk space <10% available

**Response Steps**:
1. Check disk usage: `df -h`
2. Identify large files/directories
3. Clean up:
   - Old log files
   - Temporary files
   - Old database backups
4. Consider increasing disk size
5. Set up automatic cleanup if needed

**Resolution Time Target**: <2 hours

---

## Alert Response Checklist

For any alert:
- [ ] Acknowledge alert
- [ ] Check alert details and context
- [ ] Review relevant metrics and logs
- [ ] Identify root cause
- [ ] Implement fix or workaround
- [ ] Verify resolution (alert clears)
- [ ] Document incident and resolution
- [ ] Update runbook if needed

## Escalation

If alert cannot be resolved within target time:
1. Escalate to senior engineer or on-call
2. Document what has been tried
3. Provide context and logs
4. Request assistance with specific issue

## Prevention

Regular monitoring of:
- Error rates trending upward
- Cost trends exceeding budget projections
- Performance degradation patterns
- Resource usage trends

Set up proactive alerts for trends before they become critical.
