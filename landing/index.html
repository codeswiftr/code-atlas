Getting started

Up and running in three steps

No data pipeline to set up. No schema to define. Code Atlas reads the sessions Claude Code already writes.

1

Connect your session directory

Provide your Claude Code projects path via the API or the web UI. Code Atlas scans existing sessions on first connect, then watches for new ones in the background.

POST /api/v1/sessions/import
{ "path": "~/.claude/projects" }
2

Graph builds automatically

Each session is parsed, entities are extracted (files, functions, errors, tools), and edges are created. Embeddings are generated for vector similarity. Processing takes under 2 seconds per session.

Entities: File · Function · Bug · Tool · Decision · Session
3

Query, visualize, ask

Use the graph explorer to browse visually, the search API to query programmatically, or the Q&A endpoint to ask questions in plain English. All backed by the same graph.

GET /api/v1/qa?q=which+files+have+the+most+recurring+bugs
Query interface

Write Cypher.
Get answers.

The graph query API accepts Cypher — the same language Neo4j developers already know. Or use the REST search endpoint and let the hybrid engine choose the best strategy.

  • Find every session that touched a specific file, ordered by recency
  • List bugs introduced in the same session as a particular function edit
  • Identify which tool calls appear most often before a test failure
  • Retrieve sessions semantically similar to a description you write
  • Ask freeform questions — the RAG layer grounds answers in graph context
cypher — code-atlas query 
// Sessions that touched auth files AND fixed a bug
MATCH (s:Session)-[:MODIFIED]->(f:File),
      (s)-[:FIXED]->(b:Bug)
WHERE f.path CONTAINS 'auth'
RETURN s.id, s.date, f.path, b.description
ORDER BY s.date DESC
LIMIT 20

// Most error-prone files in the last 30 days
MATCH (f:File)<-[:MODIFIED]-(s:Session)-[:INTRODUCED]->(e:Error)
WHERE s.date > date() - duration('P30D')
RETURN f.path, count(e) AS error_count
ORDER BY error_count DESC

// Tool usage before test failures
MATCH (t:Tool)<-[:USED]-(s:Session)-[:HAD_OUTCOME]->
      (o:Outcome {status: 'test_fail'})
RETURN t.name, count(s) AS times
ORDER BY times DESC

FAQ

Common questions

Where does Code Atlas store my session data?
Session data is stored in your account's isolated PostgreSQL database on Railway. Graph relationships use a Neo4j-compatible layer (PgGraph). No session content is shared between accounts. You can delete your data at any time from the dashboard.
Does it work with session logs from other AI coding tools?
Currently Code Atlas is optimized for Claude Code's session format (JSONL conversation logs). Support for Cursor, Copilot, and OpenCode session formats is on the roadmap. If your tool writes structured conversation logs, contact us — the ingestion pipeline is extensible.
What does "entity extraction" actually produce?
Code Atlas parses each conversation turn and extracts six entity types: File (paths mentioned or edited), Function (function/method names), Bug (error messages and stack traces), Tool (Bash, Read, Write, Edit calls), Decision (architectural choices noted in the session), and Session (the conversation itself). Relationships like MODIFIED, INTRODUCED, FIXED, and USED are created between them.
I already have 500+ sessions. How long does the initial import take?
Import is parallelized. At typical session sizes (10–80 conversation turns), 500 sessions process in roughly 3–8 minutes. The UI shows a live progress bar. You can start querying as sessions finish — you don't need to wait for the entire import to complete.
Can I use the graph API from my own tooling?
Yes. Every operation available in the UI is exposed via the REST API. Authentication uses API keys with per-key rate limiting. The Pro tier includes 10,000 requests/day per key, with additional keys available. Interactive API docs are at https://atlas.codeswiftr.com/api/docs.
How is this different from just searching my session files with ripgrep?
rg finds text. Code Atlas finds relationships. You can ask "show me all sessions where a bug in auth.go was fixed the same day it was introduced" — that requires graph traversal, not text search. The vector layer adds semantic similarity: finding sessions "about" a concept even when the exact words differ. The RAG endpoint synthesizes answers across multiple sessions, with citations.
